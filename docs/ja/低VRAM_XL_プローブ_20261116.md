# XL(4B DiT)2 本を 16GB GPU に収める — 低 VRAM 化プローブの記録(2026-11-16)

対象 GPU: RTX A4000(16GB、sm_86)。比較基準は同じ seed の bf16(RTX PRO 6000 ではなく A4000 上で測った bf16)。
H3(diffusers-movie-server の 48gb-pruned-lowvram)で得た知見「INT8 は読み込み順と compile の当て方で効き方が決まる」を ACE-Step 1.5 に当てた。
スクリプトは `probes/`(試聴用の音声は 11-17 に削除)。

## 結論

- **xl-turbo + xl-sft の両方を INT8(int8_weight_only)で常駐させ、LM 0.6B(pt)を足して A4000 で成立**。
  API サーバ経由の実測: 常駐 11.4GB、生成中の GPU 全体ピーク 13.7GB(turbo 60 秒 + LM thinking)/ 13.3GB(sft 60 秒 32 step)。
- 既定は `int8_weight_only` + compile なし。生成時間は bf16 比 +16%、音は bf16 に最も近い(log-mel 相関 0.987)。
- `w8a8_dynamic` は VRAM が同じで、decoder を compile すれば bf16 と同速になるが、初回に約 5 分の compile が入り、音も bf16 から離れる(相関 0.927)。
- 起動は `./run_api_server_xl_lowvram.sh`(環境変数 `ACESTEP_QUANTIZATION` / `ACESTEP_COMPILE_MODEL` で切り替え)。

## 直した 3 点(どれも元の実装では INT8 が 16GB で成立しなかった原因)

1. **API サーバは量子化を渡していなかった**(`acestep/api/startup_model_init.py`、`acestep/api/http/model_init_service.py`)。
   `initialize_service(quantization=...)` を一切渡さず、常に bf16。`ACESTEP_QUANTIZATION` 環境変数を通した(値は CLI の `--quantization` と同じ。`none` で無効)。
2. **読み込み順**(`acestep/core/generation/handler/init_service_loader.py`)。bf16 で GPU に載せてから量子化していたので、
   XL 1 本で読み込みピーク 12.2GB(常駐 10.8GB)。2 本目を読む瞬間に「1 本目 INT8 5.4GB + 2 本目 bf16 9GB」で溢れる。
   CPU 上で量子化してから GPU へ移す順に変えた。ピーク = 常駐(5.45GB → 2 本で 10.9GB)になった。
3. **compile と量子化の相性**(同ファイル)。
   - `torch.compile(self.model)` の後に `quantize_` すると、モジュール名が `_orig_mod.decoder…` になりフィルタが `decoder` を見つけられず、**量子化が黙って no-op**(int8wo+compile の結果が bf16 と常駐・速度ともに同一だった)。フィルタで `_orig_mod` を無視するようにし、量子化を compile の前に移した。
   - そもそも生成は `model.generate_audio()` → `model.decoder(...)` で、`torch.compile(model)` は `forward` しか包まないので拡散ループに効いていなかった(bf16 で compile あり/なしが同じ 15.0 秒)。`model.decoder.forward` を compile するようにした。

## 実測(xl-sft、60 秒、32 step、guidance 7、seed 12345、A4000)

| 構成 | 常駐 | 読み込みピーク | 生成ピーク | 生成時間 | bf16 との log-mel 相関 |
|---|---|---|---|---|---|
| bf16(基準) | 10.77GB | 12.17GB | 11.27GB | 15.0s | 1.000 |
| int8wo + compile(旧実装、no-op) | 10.77GB | 12.17GB | 11.27GB | 14.8s | 1.000(bf16 と同一) |
| w8a8、compile なし | 6.87GB | 9.41GB | 7.37GB | 29.5s | 0.927 |
| w8a8、CPU 量子化 → compile(旧 model 単位、効かず) | 6.87GB | 8.26GB | 7.43GB | 29.1s | 0.927(GPU 量子化とビット一致) |
| w8a8、CPU 量子化 → **decoder compile** | 6.87GB | 8.26GB | 7.43GB | **15.4s**(初回 299s) | 0.927 |
| w8a8、層ごと compile | 6.87GB | 8.26GB | 7.45GB | 29.4s(効かず) | — |
| **int8wo、CPU 量子化、compile なし** | 6.88GB | 8.27GB | 7.41GB | **17.4s** | **0.987** |
| int8wo + decoder compile | 6.88GB | 8.27GB | — | **42.6 s/step で停止同然**(600 秒で打ち切り) | — |

## 使わないと決めたもの・注意

- **int8wo + compile は A4000 で使わない**(42 秒/step)。torchao の weight-only INT8 を inductor に通すと、この GPU では極端に遅い経路に落ちる。
- w8a8 + compile を使うなら `ACESTEP_GENERATION_TIMEOUT=1800` にしないと初回リクエストが 600 秒の打ち切りに当たる。
- 量子化は decoder の Linear だけ。VAE・テキストエンコーダ・LM は bf16 のまま(CPU 退避で逃がす)。
- 音の評価は 1 seed・60 秒のみ。採用前に数 seed・長尺(240 秒)・batch 2 で聴き比べること。
- 2B(acestep-v15-turbo/base)でも同じ修正が効く(量子化が API に渡るようになったので、`ACESTEP_QUANTIZATION=int8_weight_only` を付ければ 16GB 階層の既定どおりの挙動に近づく)。未測定。

## 追試: sft の長尺・複数本(両方常駐 + LM 0.6B、A4000、API 経由、32 step)

サーバは workers=1 でジョブを順に処理するので、2 本の DiT が同時に走ることはない。問題は sft(CFG で実効 2 倍)の活性化メモリ。

| 長さ × 本数 | 結果 | GPU 全体ピーク | 所要 |
|---|---|---|---|
| 240 秒 × 3 | 成功 | 14.9GB | 183 秒 |
| 360 秒 × 3 | 成功 | 15.4GB | 285 秒 |
| 600 秒 × 3 | **OOM**(836MB の確保に失敗、`PYTORCH_ALLOC_CONF=expandable_segments:True` でも同じ) | 16.0GB | — |
| 600 秒 × 2 | 成功(expandable_segments あり) | 15.8GB | 328 秒 |

- OOM の場所は torchao の INT8 weight-only Linear(活性化が大きいとき)。ジョブは status=2 で返り、**サーバは生きていて次のジョブは成功する**(OOM 直後に 600 秒 × 2 と turbo 30 秒が成功)。
- 両方常駐の目安: **sft は 3 本なら 360 秒まで、600 秒は 2 本まで**。いずれもピークが 15GB 前後で余裕は 0.5〜1GB しかない。
- 注意: `offload_to_cpu=1` のときは生成前の VRAM 見積もり(pre-flight)が**スキップされる**ので、入らないリクエストは事前に拒否されず OOM で失敗する。
- 余裕を作る案(未実装): (a) sft 専用サーバにする(turbo を常駐させなければ −5.4GB で 600 秒 × 3 も入る見込み)、(b) 使っていない方の DiT をリクエスト中だけ CPU へ退避する(INT8 5.4GB の往復で数秒)。

## 追試 2: 300 秒 × 3 本(1 リクエスト、batch 3)の sft を速くする(両方常駐 + LM 0.6B、A4000、API 経由)

| 構成 | 1 step | 所要(壁時計) | ピーク |
|---|---|---|---|
| int8wo、32 step(基準) | 6.1s | 231s | 14.4GB |
| **int8wo、24 step** | 6.2s | **186s(−19%)** | 14.7GB |
| w8a8 + decoder compile、32 step(warmup 後) | 7.1s + 途中の再 compile | 458s | 15.0GB |
| w8a8 + decoder compile、24 step | 7.1s | 222s | 15.0GB |

- 壁時計のうち拡散以外(テキスト条件・VAE decode・mp3 化、3 本 × 300 秒)が約 35 秒。
- **w8a8 + compile はこの作業量では負け**。60 秒 × 1 本では bf16 と同速だったが、batch 3 × 300 秒では 1 step 7.1 秒(int8wo 6.1 秒)で、しかも長さや batch が変わるたびに再 compile が走る(初回 578 秒、2 回目も 458 秒)。実運用では使わない。
- **`cfg_interval_start/end` は速度に効かない**。XL の `generate_audio` は CFG の有無に関わらず decoder を常に 2 倍 batch で回し、区間は混ぜ方だけを切り替える(`modeling_acestep_v15_xl_base.py` の `apply_cfg_guidance`)。1 step は 6.21 秒で変わらなかった。速くしたいなら step 数だけが効く。
- 残る手: step をさらに減らす(16〜20。音は要確認)、turbo に切り替える(60 秒で 3 倍速)、CFG 区間外で decoder を 1 倍 batch で回す改修(未実装、区間を 0〜0.7 にすれば約 15% の見込み)。
- 試聴用の音声は 11-17 に削除(`probes/` のスクリプトで再生成できる)。

## 追試 3: 同じ seed・同じ 3 曲で方式を比べる試聴セット(300 秒 × 3 本、32 step、seed 101/202/303)

- **注意**: API は `use_random_seed` の既定が true で、`seed` だけ渡しても無視される。固定するには `use_random_seed=false` と `seed="101,202,303"`(本数ぶんをカンマ区切り)。追試 2 の試聴は seed が毎回ランダムだったので、方式ではなく別の曲を比べていた。
- seed を固定すれば int8wo / w8a8 / w8a8+compile とも 3 回の出力は完全に同一(相関 1.000)。再現性の問題はない。
- `probes/`(音声は削除済み)。
  bf16 は A4000 では入らず(sft 1 本 bf16 + 300 秒 × 3 本で OOM)、RTX PRO 6000 で作った基準。
- 時間と VRAM(A4000、両方常駐): int8wo 234 秒 / 14.4GB、w8a8(compile なし)363 秒 / 15.8GB。w8a8 は活性化の量子化ぶんメモリも多い。
- bf16 との log-mel 相関(300 秒): track0/1/2 で int8wo 0.912 / 0.885 / 0.921、w8a8 0.918 / 0.891 / 0.919。int8wo と w8a8 の間は 0.93〜0.94。
  60 秒の測定(同じ A4000 上の bf16 が基準)では int8wo 0.987 / w8a8 0.927 と差があったが、ここでは基準が別 GPU(RTX PRO 6000)なので
  GPU 間の数値差が乗り、方式の差は数値では見えない。**判断は試聴で**。

## 追試 4: 時間の内訳と A6000 の記憶との照合(int8wo、両方常駐、A4000、API 経由、モデルは読み込み済み)

測定にモデル読み込みは含まれない(サーバ起動後、数分おいてリクエスト)。サーバ内訳(`time_costs`):

| リクエスト | 拡散(1 step) | 拡散合計 | 壁時計 | 拡散以外(decode・mp3・キュー) |
|---|---|---|---|---|
| sft 180 秒 × 1、32 step | 1.19s | 38s | 52s | 14s |
| sft 180 秒 × 3、32 step | 3.59s | 115s | 140s | 25s |
| sft 300 秒 × 3、32 step | 6.17s | 197s | 234s | 36s |
| turbo 180 秒 × 1、8 step | 0.64s | 5.1s | 20s | 15s |
| turbo 180 秒 × 3、8 step | 1.77s | 14s | 40s | 26s |

- 1 step の時間は本数×長さにほぼ比例(batch 3 で 3.0 倍)。batch にまとめても拡散は速くならず、節約できるのは拡散以外の固定費だけ(3 本で 156 → 140 秒)。
- A6000 で「3 分 1 本 ≈ 30 秒」の記憶に対し A4000 は 52 秒。bf16 tensor の理論値で A6000 は A4000 の約 2 倍なので、INT8 weight-only(演算は bf16)の分を含めて妥当。300 秒 × 3 本 = 180 秒 × 1 本の 5 倍の仕事なので 234 秒は計算どおりで、異常ではない。
- 拡散以外の 14〜36 秒(VAE decode・mp3 化・キュー)は長さと本数で増える。短縮するなら音声形式(wav/flac)や decode のチャンク設定を見る。

## 追試 5: 速さの構造(どこを削れば効くか)

### A4000 の INT8 行列積(1 step の形 M=9000 で素のまま測定)

| 形(K×N) | bf16 行列積 | 素の `_int_mm` | torchao int8wo | torchao w8a8 eager | torchao w8a8 compiled |
|---|---|---|---|---|---|
| 2560×2560 | 1.78ms(66 TFLOPS) | **1.10ms(107 TOPS)** | 2.07ms | 5.46ms | 2.07ms |
| 2560×9728 | 7.31ms | **4.30ms** | 8.27ms | 11.06ms | 7.75ms |
| 9728×2560 | 7.16ms | **3.71ms** | 7.49ms | 20.07ms | 8.43ms |

INT8 テンソルコアは bf16 の 1.6〜1.9 倍出る。torchao の w8a8 は活性化の量子化・逆量子化が別カーネルで、compile しても bf16 と同じ。**GPU は速いがカーネルが悪い**。
torchao 0.15 は torch 2.10 と版が合わず C++ 拡張を読めていない(警告)。

### 1 step の CUDA 時間の内訳(int8wo、300 秒 × 3 本、torch.profiler)

| 区分 | 割合 |
|---|---|
| 要素ごとの演算(norm・SiLU・残差・adaLN・重みの逆量子化、未融合) | **51%** |
| bf16 行列積 | 38% |
| attention(flash_attn 2) | 7% |

行列積は 4 割だけ。半分は未融合の細かい演算で、compile が効いていない状態の典型。INT8 行列積だけ 2 倍にしても全体 −20% が上限。

### compile(融合)の効き(180 秒 × 1 本、32 step、decode 込み、A4000)

| 構成 | 所要 | ピーク |
|---|---|---|
| bf16 | 49s | 11.5GB |
| **bf16 + decoder.forward compile** | **39s(−20%)**、初回 87s | 11.5GB |
| int8wo(compile なし) | 53s | 7.7GB |
| int8wo + compile | 42 s/step で停止同然(追試 1) | — |

融合だけで −20%。ただし bf16 は 1 本で 11.5GB なので両方常駐も 300 秒 × 3 本も A4000 に入らない。
**「INT8 の重み(VRAM)+ compile(融合)」の組が必要で、torchao の int8wo だけがそれを壊している。**

### 次の候補(probe-first)

1. 自前の INT8 weight-only Linear(int8 重み + スケールのバッファ、forward で bf16 に戻して matmul)に差し替え、decoder を compile。
   torchao のテンソルサブクラスを経由しないので inductor が普通に扱える見込み。狙い: int8wo の音(bf16 と相関 0.987)のまま bf16+compile の速さ(−20〜25%)。
2. comfy-kitchen `int8_linear`(W8A8、活性化の量子化と Hadamard 回転 convrot と直前の活性化関数をカーネル内で融合。H3 の int8dyn-convrot と同系)。
   行列積 1.7〜1.9 倍 + 融合で、1 に加えてさらに −15〜20% の見込み。音は W8A8 なので回転ありで要確認(H3 では回転ありで合格)。
   パッケージは H3 の venv(torch 2.9)に 0.2.37 が入っている。この venv は torch 2.10 なので動作確認から。

## 追試 6: 候補 1(自前 INT8 weight-only Linear `int8_plain` + decoder compile)— **本番の形では効かず**

- 実装: `acestep/core/generation/handler/int8_plain_linear.py`(`ACESTEP_QUANTIZATION=int8_plain`)。音は bf16 と相関 0.991 で torchao int8wo と同等。
- 180 秒 × 1 本: torchao int8wo 53s → int8_plain + compile 43.7s(−18%)。
- **300 秒 × 3 本(API)**: torchao int8wo 6.17 s/step → int8_plain + compile 6.93 s/step(+12%、遅くなる)。
- graph break は 0(decoder.forward は 1 グラフ・4700 op)なので「融合できていない」のではなく、batch 3 では融合しても速くならない。

### 測定の落とし穴(記録しておく)

- `offload_to_cpu=False` のスタンドアロンでは VRAM ガード(`memory_utils._auto_reduce_batch`)が **batch を黙って 1 に落とす**(A4000 の空き 8GB では XL-SFT 300 秒の見積もり 3.7GB/本 → 1 本)。
  スタンドアロンが「サーバの 2 倍速い」ように見えたのはこれ。サーバ(offload=True)は tier 上限内なら落とさない。本数は出力ファイル数で必ず確かめる。
- API の `seed` は `use_random_seed=false` を付けないと無視される(追試 3)。
- プロファイルの窓に VAE decode を含めると、Snake 活性化(sin / pow / mul / add、1 万回超)と conv1d が「細かい演算」の大半を占めて DiT の内訳が見えなくなる。step 数を変えた 2 回の差分で DiT だけを出す。

### DiT 1 step の本当の内訳(int8wo、300 秒 × 3 本、flash-attn、8 step と 2 step の差分 ÷ 6)

| 区分 | 1 step | 割合 |
|---|---|---|
| bf16 行列積 | 3.05s | 48% |
| 要素ごとの演算(adaLN・RMSNorm・SiLU・残差・rotary・KV の結合など) | 2.60s | 41% |
| attention(flash_attn 2) | 0.63s | 10% |
| 合計 | 6.3s | |

- 行列積が INT8 で 1.7 倍になれば 3.05 → 1.8s、1 step −20%(300 秒 1 曲 66s → 53s、**−13 秒/曲**)。これが候補 2(comfy-kitchen W8A8 + 回転)の上限。音は W8A8 なので要試聴。
- 要素ごとの演算 41% は compile で縮まなかった(理由未特定。flash-attn のカスタム op や KV cache の結合で融合が分断されている可能性)。ここを削るには op 単位の特定が必要。
- 拡散以外(VAE decode 6.2 秒/曲、mp3 3.3 秒/曲)は別口で −5 秒/曲ほど取れる(flac 化、VAE decoder の compile かチャンク拡大)。

## 追試 7: torchao w8a8 + decoder compile(max-autotune)— 300 秒 × 1 本、32 step、A4000、SDPA

ユーザー提案(`int8_dynamic_activation_int8_weight` + `torch.compile(mode="max-autotune")`)の検証。FP8 は A4000(sm_86)に FP8 テンソルコアが無いので対象外。
A4000 は SM 48 で inductor の「大きい GPU」判定(68 以上)を下回り max-autotune の GEMM 探索が無効になるため、`torch._inductor.utils.is_big_gpu` を True に差し替えて測った。

| 構成 | 1 step | 1 曲(32 step、decode 込み) | bf16 との log-mel 相関 | 備考 |
|---|---|---|---|---|
| bf16 | 2.62s | 94.6s | 1.000 | 11.1GB、両方常駐は不可 |
| torchao int8wo(現行既定) | 2.70s | 97.0s | 0.974 | |
| w8a8 + decoder compile(既定モード) | 2.28s | — | — | 初回 338s |
| **w8a8 + decoder compile(max-autotune-no-cudagraphs、big-gpu 強制)** | **2.25s** | **84.2s(−13%)** | 0.922 | 初回 390s、再 compile は初回の 1 回(KV cache 有無の 2 グラフ)、2 回目以降は同一出力(相関 1.000) |

- 速さ: 1 曲 97 → 84 秒(−13 秒)。ご希望の「1 曲 10 秒」に届く。
- 音: W8A8 は bf16 から離れる(0.922。int8wo は 0.974)。試聴は `probes/`(音声は削除済み)(同じ seed の bf16 / int8wo / w8a8)。
- 運用上の注意: 初回リクエストに約 6.5 分の compile(`ACESTEP_GENERATION_TIMEOUT=1800` 必須)。長さや本数が変わると再 compile(追試 2 で 300 秒 × 3 本は 458 秒)。1 本固定・長さの刻みを揃える運用なら実用。
- 未実装: サーバで max-autotune と big-gpu 強制を選ぶ設定(今はプローブのみ)。

## 追試 8: 長さが毎回変わる運用で compile は成立するか — **成立しない**(torch 2.10 + この decoder)

300 / 287 / 243 / 300 秒を 1 プロセスで続けて生成(w8a8 + decoder compile、max-autotune、8 step):

| 方式 | 結果 |
|---|---|
| 既定(自動 dynamic: 2 つ目の形で長さを可変に切替) | 287 秒・243 秒で **InductorError(AssertionError、記号長の式が負になる)** で失敗。300 秒に戻ると成功 |
| `dynamic=True` | 最初の 300 秒で **600 秒のタイムアウト**(compile が終わらない、または停止) |

- 固定形の compile は長さ 1 秒刻みごとに約 6 分の compile。inductor のディスクキャッシュは効く(同じ形の 2 プロセス目は 67 秒)が、形の数だけ積み上がる。
- 長さを 10 秒刻みに丸めてバケット化すれば形は有限になるが、duration は条件づけにも入るので曲の終わり方が変わる。採用しない。
- **結論: 秒単位で長さが変わる運用では compile を前提にできない。** compile 無しで INT8 の行列積を速くするには、eager で動く融合カーネル(comfy-kitchen `int8_linear`、候補 2)しか残らない。

## 11-17: 戦略変更 — GPU には DiT を 1 本だけ(排他常駐、`ACESTEP_DIT_RESIDENCY=exclusive`)

ユーザーの方針: sft だけ常駐、turbo は要求時に、次の sft で turbo を外す。長さは毎回変わる、1 曲ずつでよい、mp3 と CoT は残す。

### 実装

- `acestep/api/dit_residency.py`: `DitResidency.activate(handler)` をジョブ実行スレッドの先頭(`job_execution_runtime._blocking_generate`)で呼ぶ。
  今 GPU にいる DiT を `park`(CPU の **pinned 原本に差し替えて GPU 側を捨てるだけ**。重みは推論で変わらないので原本は初回に 1 度作る)、要求された DiT を pinned から GPU へ(`activate`)。
- 起動(`startup_model_init.py`): 2 本目以降は `offload_dit_to_cpu=True` で CPU に読み、そのまま pinned 化して退避。1 本目は GPU に置き、`prime` で pinned 原本だけ先に作る(初回切替の 8 秒を起動時へ)。
- 起動スクリプト `run_api_server_xl_swap.sh`: sft(primary、bf16)+ turbo(2 本目、bf16)。GPU に 1 本ずつなので量子化は不要。VAE/TE/LM は従来どおり CPU 退避。
- 単体テスト `acestep/api/dit_residency_test.py`。

### RMSNorm の融合(マイクロベンチ、実際の形)

| 形 | eager(Qwen3RMSNorm) | `F.rms_norm`(1 カーネル、weight 内側) | 2 カーネル版(`weight * F.rms_norm(x, None)`、Qwen3 と同じ丸め順) |
|---|---|---|---|
| hidden [2,3750,2560] | 1.79ms | 0.28ms(bf16 の 1 ulp 差、最大 3.1e-2) | 0.48ms(1 ulp 差が残る: fp32 の縮約順が違うため) |
| q/k [2,3750,16,128] | 1.44ms | 0.25ms(同上) | 0.41ms(**bit 一致**) |

- `F.rms_norm` は CUDA では融合カーネル(`vectorized_layer_norm`)1 個。内部 fp32。
- 見込み: RMSNorm 0.40s → 0.06〜0.11s で 1 step −15%、300 秒 1 曲で約 −9〜10 秒(61 → 51 秒)。
- 音: 計算は同じで差は bf16 の最小桁(1 ulp)の丸めのみ。ただし拡散を 32 step 通すとその差が増幅され、**同じ seed でも波形は少し別の実現になる**(compile で見た bf16 対 bf16+compile の相関 0.985 と同じ種類)。「劣化」ではないが「同一」でもない点は試聴で確認する。
- 次点: attention 内のコピー(10%)、rotary(4%)、SwiGLU(3%)は融合しても合計 −5% 程度。

### RMSNorm 融合の実装と実測(11-17)

- 実装: `acestep/core/generation/handler/fused_rmsnorm.py`。ローダ(`_load_main_model_from_checkpoint`)が `ACESTEP_FUSED_RMSNORM` を読み、DiT モデル内の RMSNorm(293 個)の forward を `F.rms_norm` ベースに差し替える。LM には触れない。`exact` = `weight * rms_norm(x)`(Qwen3 と同じ丸め順)、`fast` = weight をカーネル内で。

## 11-17: 同時実行(`ACESTEP_QUEUE_WORKERS` / `ACESTEP_API_WORKERS` ≥ 2)への対応

運用メモ(同時実行 2〜4)の前提で確かめたところ、2 つの穴があった。
1. **LM(CoT)のハンドラにロックが無い**(オリジナルの問題): 2 ジョブが同時に LM を呼ぶと CUDA の device-side assert → CUDA コンテキストが壊れて以後全件失敗。
   → `acestep/llm_concurrency.py` の `@serialized` で LM の公開エントリ 4 つ(`generate_with_stop_condition` / `understand_audio_from_codes` /
   `create_sample_from_query` / `format_sample_from_input`)をハンドラごとの RLock で直列化。DiT の生成は並列のまま。
2. **排他常駐が単一スレッド前提**だった → `DitResidency.use(handler)`(ジョブ実行スレッドが入る)で、GPU 上のモデルへのジョブは並列、
   別モデルの要求は実行中のジョブを待ってから切替、切替待ちがある間は新規ジョブも待つ(飢餓防止)。
3. 同時実行時はテキストエンコーダの退避(`_load_model_context`)もスレッド間で競合するので常駐にする(`ACESTEP_RESIDENT_COMPONENTS=vae,text_encoder`。
   `run_api_server_fast.sh` は QUEUE_WORKERS>1 のとき自動で設定)。

実測(A4000、QUEUE_WORKERS=2、7 ジョブを一度に投入、60 秒): 全件成功、`dit_model` も要求どおり。2B ×2 は並列(7.0s / 10.0s 完了)、
xl-sft への切替は 2B の 2 本が終わってから(25.3s)、以後 2B ↔ xl-sft ↔ xl-turbo を順に切替(切替 0.9〜1.7s)。起動後 14.1GB(TE 常駐で +1.1GB)。
16GB では XL-sft の 300 秒 × 2 並列は活性化で溢れる恐れがあるので、A4000 の既定は QUEUE_WORKERS=1 のまま。
